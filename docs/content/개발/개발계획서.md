[[기획서]]에서 정의한 기능은 대부분 구현되어 있으며, 코드는 Turborepo
모노레포 + FSD(Feature-Sliced Design) 구조로 정리되어 있습니다. 백엔드
배포는 Render로 전환되었고 상품 이미지는 Cloudflare R2에 업로드하는
방식으로 바뀌었으며, 관리자 인증(공유 비밀번호 + 세션)도 추가됐습니다.
이 프로젝트는 포트폴리오용이라 실제 결제 게이트웨이(PG) 연동은 하지
않기로 확정했습니다 — 결제는 수단을 고르는 화면([[결제수단선택]])까지만
구현하고, 실제로 돈이 오가는 연동은 범위 밖입니다. 테스트 도입은
백엔드(Vitest + Supertest + 인메모리 MongoDB)에 이어 프론트엔드
(Vitest, 장바구니 스토어 등 순수 로직 위주)까지 마쳤습니다.

## 현재 아키텍처

### 모노레포 구조
- `apps/frontend` — Next.js(App Router) 키오스크 화면
- `apps/backend` — Express + MongoDB REST API 서버
- `packages/types` — 프론트/백엔드가 공유하는 계약 타입(Product, Order,
  CreateOrderInput 등)
- `packages/eslint-config`, `packages/typescript-config` — 공용 설정
  (한때 있던 `packages/ui`는 아무 데서도 쓰이지 않는 Turborepo 기본
  보일러플레이트라 삭제함)

### 프론트엔드 (FSD)
`apps/frontend/src/`가 다음 레이어로 구성됩니다.
- `app` — Next.js 라우팅, 각 `page.tsx`는 `views/` 슬라이스를 조립만 함
- `views` — 라우트별 화면 조합 (`home`, `admin`, `kitchen`). 원래 FSD
  표준 명칭은 `pages`이지만, Next.js App Router가 `pages/` 디렉터리를
  레거시 Pages Router로 인식해 라우팅 충돌이 나기 때문에 이
  프로젝트에서는 `views`로 씁니다. `kitchen`은 `/kitchen` 라우트 —
  주문 확인/완료 처리만 담당하는 화면으로, `/admin`과 세션은 공유하되
  화면은 분리돼 있습니다(아래 마일스톤 참고).
- `widgets` — `order-type-select`(첫 화면의 매장/포장 선택),
  `product-list`, `order-summary`, `add-product-form`(이미지 파일을
  선택하면 백엔드에 업로드하고 반환된 R2 공개 URL을 미리보기와 함께
  씀), `manage-product-list`(`selectedCategory`로 필터링, 특정
  카테고리를 골랐을 때만 드래그 손잡이 + ▲▼ 순서 변경 UI 표시),
  `manage-category-list`("메뉴 관리" 탭 안의 카테고리 칩 바 — 클릭 시
  필터, 추가/인라인 수정/삭제/드래그(포인터 이벤트) 순서 변경 — ◀▶
  버튼은 뺌),
  `order-list`(주방 화면 "진행중 주문"/"지난 주문" 탭 — `status`
  prop으로 전환, 10초 폴링 + 수동 새로고침, 완료 버튼), `manage-ad-list`(광고
  관리 탭 — 썸네일 그리드 + 추가/수정 겸용 `AdForm`(모달), 드래그
  손잡이 + ◀▶ 순서 변경 UI), `sales-dashboard`(판매 통계 탭 — 연도
  선택 버튼(최근 5개년) + SVG 꺾은선 그래프로 그 해 월별 판매량 추이,
  점 클릭으로 고른 달의 메뉴별 판매 순위(데스크탑에서 2~3열 그리드).
  별도 상태 관리 없이 위젯 로컬 상태로 데이터 조회)
- `features` — `order-type`(매장/포장 선택 상태), `cart`(장바구니
  담기/주문 제출 — `makeCartItemId`로 상품 id+옵션 조합의 장바구니
  전용 식별자를 만들어, 같은 상품이라도 선택한 메뉴별 커스텀 옵션이
  다르면 다른 줄로 취급), `product-management`
  (메뉴 등록/수정/품절/재고 조정/
  삭제/순서 변경 — `adjustStock`, `moveProduct`/`reorderLocally`/
  `commitProductOrder`가 전부 같은 카테고리 안에서만 재배치),
  `category-management`(카테고리 추가/수정/삭제/순서 변경),
  `admin-auth`(관리자 로그인/로그아웃, 세션 확인),
  `ad-management`(광고 배너 추가/수정/삭제/순서 변경)
- `entities/product` — 상품 CRUD API, `ProductCard` UI(클릭 시 옵션
  선택 모달 — `product.hasTemperatureOption`/`hasMagicSpellOption`이
  켜져 있을 때만 온도/마법의 주문 콤보박스, `product.options`는
  체크박스, [[옵션조합관리]] 참고), `TEMPERATURE_OPTIONS`/
  `MAGIC_SPELL_OPTIONS` 상수, `ProductOptionsEditor` UI(온도/마법의
  주문 노출 체크박스 + 메뉴 옵션 이름+추가금 입력 줄 추가/삭제, 메뉴
  추가/수정 폼 양쪽이 공유)
- `entities/category` — 카테고리 CRUD API(`getCategories`,
  `createCategory`, `updateCategory`, `deleteCategoryById`)
- `entities/order` — 주문 조회/완료 처리 API(`getOrders`,
  `completeOrder`)와 `OrderCard` UI, 판매 통계 API(`getMonthlySalesSummary`,
  `getProductSalesRanking`)
- `entities/ad` — 광고 CRUD API(`getAds`/`createAd`/`updateAd`/
  `deleteAdById`/`reorderAds`)와 고객 화면용 `AdBanner` UI(`order` 순
  자동 전환, 5초 간격, 광고 0개면 렌더링 안 함)
- `shared` — 공용 axios 인스턴스(`shared/api`), 상품/광고가 공용으로
  쓰는 이미지 업로드 함수(`shared/api/uploadImage`), API base URL 설정
  (`shared/config`), 도메인 지식 없는 범용 UI 컴포넌트(`shared/ui` — 현재
  `Modal`)

상태 관리는 Zustand(`features/cart`, `features/product-management`,
`features/category-management`, `features/ad-management`)를 사용합니다.

### 백엔드
- Express 5 + Mongoose, TypeScript로 작성
- REST 엔드포인트: `GET/POST /api/categories`,
  `PUT/DELETE /api/categories/:id`, `PATCH /api/categories/reorder`
  (`GET`은 공개, 나머지는 `requireAdmin`. 이름 수정/삭제 시 해당
  카테고리를 쓰는 상품도 함께 갱신/삭제),
  `GET/POST /api/products`(`GET`은 `category → order` 순 정렬),
  `PUT /api/products/:id`, `PATCH /api/products/reorder`(같은 카테고리
  상품 id 배열로 순서 재배열, `requireAdmin`),
  `PATCH /api/products/:id/sold-out`(품절 여부 토글),
  `PATCH /api/products/:id/stock`(재고 수량 절대값 설정 + 0 이하/초과에
  따른 자동 품절 처리/해제),
  `DELETE /api/products/:id`,
  `GET /api/orders`(최신순 조회, `status=pending|completed` 쿼리 필터,
  `requireAdmin`으로 보호), `PATCH /api/orders/:id/complete`(완료 처리),
  `POST /api/orders`(요청 바디에 매장 내/포장 구분 `orderType` 포함.
  성공 후 `decrementStockForOrder`로 재고 추적 상품만 자동 차감),
  `GET /api/orders/stats/monthly?year=YYYY`(그 해 1~12월 월별 판매량/
  매출 추이, 생략하면 올해, 없는 달은 0으로 채움), `GET
  /api/orders/stats/monthly/:month`(그 달 메뉴별 판매 순위, 판매량
  내림차순) — 둘 다 `requireAdmin`으로 보호, 완료 여부와 무관하게
  생성된 모든 주문을 집계,
  `GET/POST /api/ads`, `PUT/DELETE /api/ads/:id`, `PATCH
  /api/ads/reorder`(광고 id 배열로 순서 재배열)(`GET`은 공개, 나머지는
  `requireAdmin`. `GET`은 `order` 순 정렬),
  `POST /api/uploads`(이미지 파일을 Cloudflare R2에
  업로드하고 공개 URL 반환 — 상품/광고 이미지가 공용으로 씀),
  `GET /health`(DB에 접근하지 않는 가벼운
  헬스체크 — Render 자체 헬스체크와 무료 티어 슬립 방지용 외부 핑에 사용),
  `POST /api/admin/login`/`GET /api/admin/session`/`POST /api/admin/logout`
  (관리자 로그인/세션 확인/로그아웃)
- `packages/types`의 `CreateOrderInput`, `UploadImageResponse`,
  `AdminLoginInput`, `AdminSessionResponse`, `UpdateSoldOutInput`,
  `CategoryInput`, `ProductInput`, `ReorderProductsInput`, `Ad`,
  `AdInput`, `ReorderAdsInput`, `UpdateStockInput`, `MonthlySalesSummary`,
  `ProductSalesRanking`을 프론트엔드와 함께 사용해 요청/응답
  계약을 공유.
  `Product.category`는 고정 union(`'coffee'|'ade'|'dessert'`)이 아니라
  `string`으로 바뀌어 관리자가 등록한 어떤 카테고리 이름도 가리킬 수
  있음. `Product.order`(같은 카테고리 안에서의 순서)가 엔티티엔 있지만
  생성/수정 요청 바디엔 필요 없어서, 요청 바디 타입을 `Omit<Product,
  '_id'>` 대신 별도 `ProductInput`으로 분리함(`CategoryInput`과 같은
  패턴)
- Cloudflare R2 연동은 `src/lib/r2Client.ts`(`@aws-sdk/client-s3` 기반)에서
  담당하며, `multer`로 업로드된 파일을 메모리에 받아 R2로 전달
- 관리자 인증은 `express-session` + `connect-mongo`(기존 `MONGO_URI`
  재사용) 기반 세션이며, `src/middleware/requireAdmin.ts` 미들웨어가
  `POST/DELETE /api/products`, `POST /api/uploads`를 보호합니다. 세션
  쿠키를 프론트엔드(Vercel)와 주고받기 위해 CORS를 `FRONTEND_ORIGIN` 단일
  오리진 + `credentials: true`로 설정했습니다 — [[관리자인증인가]] 참고.

## 아키텍처 방향 메모 — 백엔드를 Next.js로 합치지 않고 분리 유지

**TL;DR**: 웹 키오스크뿐 아니라 향후 React Native 모바일 앱도 만들 계획이
있어([[기획서]] 범위 확장 시 반영 예정), `apps/backend`(Express)를
`apps/frontend`의 Next.js API Route로 흡수하지 않고 지금처럼 독립된
백엔드로 유지하기로 함. 지금 당장 처리할 작업은 아니고, 향후 구조를 정할
때 참고할 방향 메모.

**왜 이 논의가 나왔나**: `/admin` 관리자 인증을 만들며 프론트(Vercel)와
백엔드(Render)가 다른 오리진이라 CORS를 신경 써야 했던 걸 계기로, "차라리
백엔드를 Next.js API Route로 합쳐서 같은 오리진으로 만들면 더 간단하지
않을까"라는 질문이 나왔음.

**클라이언트가 웹 하나뿐이라면** Next.js API Route로 합치는 쪽이 실제로
더 단순했을 것(같은 오리진이라 CORS 자체가 불필요, 배포 대상도 Vercel
하나로 통합). 이 경우 `packages/types`, `packages/ui` 같은 공유 패키지와
Turborepo도 존재 의미가 줄어서 단일 Next.js 프로젝트로 단순화하는 것도
합리적인 선택지였음.

**하지만 모바일 앱 계획 때문에 결론이 바뀜**:
- React Native 앱도 결국 이 백엔드의 REST API를 호출해야 함. Next.js API
  Route도 기술적으로는 모바일에서 호출 가능하지만, 그러면 API가 "특정 웹
  프론트엔드 프로젝트의 부속물"이 되어 프론트 UI만 바꿔도 API가 같이
  재배포되는 등 결합이 생김. 웹/앱이 동등하게 의존하는 **독립된 백엔드
  서비스**로 두는 게 구조적으로 더 깔끔함.
- 앱이 웹(Next.js) + 모바일(React Native) + 백엔드(Express) 3개가 되면
  `packages/types`(공유 계약 타입)와 Turborepo 모노레포 구조가 다시
  확실한 존재 이유를 가짐 — 지금 구조를 그대로 확장하면 됨.
- **인증 방식 관련 참고**: 지금 관리자 인증(`express-session` 쿠키 기반,
  [[관리자인증인가]])은 매장 스태프가 웹으로만 쓰는 화면이라 문제없음.
  다만 앞으로 **고객용 로그인**을 만들 일이 생기면 웹/모바일 양쪽에서
  써야 하므로, 쿠키 세션보다 토큰 기반(JWT를
  `Authorization` 헤더로 전달)이 React Native와 궁합이 좋음 — 브라우저가
  아닌 앱은 쿠키 자동 관리가 안 되기 때문. 그 기능을 실제로 만들 때
  다시 검토.

**결론**: 지금 구조(Turborepo 모노레포 + `apps/backend` 분리)를 유지한다.
실시간 주방 디스플레이(KDS, WebSocket 필요)도 서버리스보다 지속 연결이
가능한 별도 서버가 유리해서 같은 결론을 지지함. 모바일 앱 착수가
확정되면 `apps/mobile`을 추가하는 흐름이 될 것.

> 이 메모는 방향성 논의 요약이며, 실제로 모바일 앱 착수가 확정되는 등
> 구조가 확정되면 `docs/decisions/`에 정식 ADR로 남기는 것을 권장합니다
> (`docs/AGENTS.md` 참고).

    `uiautomator dump`로 실측(고정 px 너비 + aspectRatio는 정상,
    퍼센트 너비 + aspectRatio는 비정상임을 직접 실험으로 확인)해
    찾아냄 — `onLayout`으로 실측한 너비를 바탕으로 `width`/`height`를
    JS에서 직접 계산하는 방식으로 교체해 해결. `docs/specs/
    009-mobile-tablet-sizing`은 이 검증까지 마치고 `complete`로 전환.
- [x] 카테고리 탭을 누르면 메뉴 목록을 맨 위로 되돌리는 기능 — 이전
  카테고리에서 스크롤해둔 위치가 그대로 남아있어 새 목록이 중간부터
  보이던 문제. 별도 스펙 없이 웹(`window.scrollTo`)과 모바일
  (`FlatList.scrollToOffset`) 양쪽에 동일하게 적용.
- [ ] 주방 화면 새 주문 웹 푸시 알림 — 지금까지 주방 화면(`/kitchen`)은
  10초 폴링으로만 새 주문을 반영했는데, 서비스워커 기반 Web Push로
  주문 즉시 OS 알림이 뜨도록 함(`docs/specs/010-kitchen-push-notification`).
  기존 폴링은 신뢰성 백업으로 그대로 유지.
  - 이 프로젝트의 Serwist 서비스워커는 사실 지금까지 **등록 코드
    자체가 없어서 전혀 동작하지 않고 있었다** — `@serwist/next`는
    `SerwistProvider`를 직접 붙여야 등록되는데 그게 빠져 있었음. 이번에
    처음으로 실제 등록되게 함.
  - Render 무료 티어(슬립 방지용 외부 헬스체크에 의존)라 WebSocket
    같은 상시 연결 방식은 이 배포 환경과 맞지 않는다고 판단해, 발송
    시점에만 요청이 오면 되는 Web Push를 선택.
  - 백엔드에 `web-push` 패키지, `PushSubscription` 모델,
    `POST /api/push/subscribe`(`requireAdmin`)/`GET
    /api/push/vapid-public-key`(공개) 추가. 주문 생성(`POST
    /api/orders`) 직후 재고 차감과 같은 자리에서 "fire and forget"으로
    알림을 보내, 알림 전송 실패가 고객의 주문 성공에 영향을 주지
    않게 함. 구독 하나가 만료(410/404)돼도 다른 구독에는 영향
    없이 독립 처리하고 만료 구독은 자동 정리.
  - `notifyKitchenOfNewOrder`는 `web-push`를 모킹한 테스트로 구독
    전체 발송/만료 구독 정리/구독 없을 때 무동작까지 검증(`pnpm
    --filter backend test` 37개 통과).
  - **실제 브라우저 알림 수신 확인은 못함** — 에뮬레이터 Chrome으로
    검증하려다 실제 사용자 Google 계정 이메일이 로그인 화면에
    자동완성되는 걸 발견하고 그 즉시 중단한 일이 있어(이후 관련
    기록 참고), 이후로는 브라우저를 직접 조작하는 검증을 하지
    않기로 함. 알림 권한 허용도 사람이 직접 눌러야 하는 단계라
    자동화하기 어려움 — 사용자가 직접 `pnpm --filter frontend build
    && pnpm --filter frontend start`(개발 서버는 서비스워커가 꺼져
    있어 안 됨)로 `/kitchen`에서 확인해야 함. 이 때문에
    `docs/specs/010-kitchen-push-notification`은 `in-progress`로 남아있음.

## 다음 우선순위 로드맵

아래 항목 중 실제 작업을 시작하는 항목은 `docs/AGENTS.md`의 SDD 워크플로우에
따라 LeanSpec으로 개별 스펙(`docs/specs/`)을 만들고 진행 상태를 추적합니다.
이 문서는 우선순위 개요만 담고, 항목별 상세 설계/작업 분해는 해당 스펙에

   참고). 필요해지면 별도 스펙으로 착수합니다.
