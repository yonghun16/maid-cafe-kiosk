[[기획서]]에서 정의한 기능은 대부분 구현되어 있으며, 코드는 Turborepo
모노레포 + FSD(Feature-Sliced Design) 구조로 정리되어 있습니다. 백엔드
배포는 Render로 전환되었고 상품 이미지는 Cloudflare R2에 업로드하는
방식으로 바뀌었으며, 관리자 인증(공유 비밀번호 + 세션)도 추가됐습니다.
다음 우선순위는 결제 연동 여부 결정과 테스트 도입입니다.

## 현재 아키텍처

### 모노레포 구조
- `apps/frontend` — Next.js(App Router) 키오스크 화면
- `apps/backend` — Express + MongoDB REST API 서버
- `packages/types` — 프론트/백엔드가 공유하는 계약 타입(Product, Order,
  CreateOrderInput 등)
- `packages/ui`, `packages/eslint-config`, `packages/typescript-config` —
  공용 설정/컴포넌트

### 프론트엔드 (FSD)
`apps/frontend/src/`가 다음 레이어로 구성됩니다.
- `app` — Next.js 라우팅, 각 `page.tsx`는 `views/` 슬라이스를 조립만 함
- `views` — 라우트별 화면 조합 (`home`, `admin`). 원래 FSD 표준 명칭은
  `pages`이지만, Next.js App Router가 `pages/` 디렉터리를 레거시 Pages
  Router로 인식해 라우팅 충돌이 나기 때문에 이 프로젝트에서는 `views`로
  씁니다.
- `widgets` — `order-type-select`(첫 화면의 매장/포장 선택),
  `product-list`, `order-summary`, `add-product-form`(이미지 파일을
  선택하면 백엔드에 업로드하고 반환된 R2 공개 URL을 미리보기와 함께
  씀), `manage-product-list`(`selectedCategory`로 필터링, 특정
  카테고리를 골랐을 때만 드래그 손잡이 + ▲▼ 순서 변경 UI 표시),
  `manage-category-list`("메뉴 관리" 탭 안의 카테고리 칩 바 — 클릭 시
  필터, 추가/인라인 수정/삭제/드래그(포인터 이벤트)·◀▶ 순서 변경),
  `order-list`(관리자 "진행중 주문"/"지난 주문" 탭 — `status` prop으로
  전환, 10초 폴링 + 수동 새로고침, 완료 버튼)
- `features` — `order-type`(매장/포장 선택 상태), `cart`(장바구니
  담기/주문 제출), `product-management`(메뉴 등록/수정/품절/삭제/순서
  변경 — `moveProduct`/`reorderLocally`/`commitProductOrder`가 전부 같은
  카테고리 안에서만 재배치), `category-management`(카테고리 추가/수정/
  삭제/순서 변경), `admin-auth`(관리자 로그인/로그아웃, 세션 확인)
- `entities/product` — 상품 CRUD API와 `ProductCard` UI
- `entities/category` — 카테고리 CRUD API(`getCategories`,
  `createCategory`, `updateCategory`, `deleteCategoryById`)
- `entities/order` — 주문 조회/완료 처리 API(`getOrders`,
  `completeOrder`)와 `OrderCard` UI
- `shared` — 공용 axios 인스턴스(`shared/api`), API base URL 설정
  (`shared/config`), 도메인 지식 없는 범용 UI 컴포넌트(`shared/ui` — 현재
  `Modal`)

상태 관리는 Zustand(`features/cart`, `features/product-management`,
`features/category-management`)를 사용합니다.

### 백엔드
- Express 5 + Mongoose, TypeScript로 작성
- REST 엔드포인트: `GET/POST /api/categories`,
  `PUT/DELETE /api/categories/:id`, `PATCH /api/categories/reorder`
  (`GET`은 공개, 나머지는 `requireAdmin`. 이름 수정/삭제 시 해당
  카테고리를 쓰는 상품도 함께 갱신/삭제),
  `GET/POST /api/products`(`GET`은 `category → order` 순 정렬),
  `PUT /api/products/:id`, `PATCH /api/products/reorder`(같은 카테고리
  상품 id 배열로 순서 재배열, `requireAdmin`),
  `PATCH /api/products/:id/sold-out`(품절 여부 토글),
  `DELETE /api/products/:id`,
  `GET /api/orders`(최신순 조회, `status=pending|completed` 쿼리 필터,
  `requireAdmin`으로 보호), `PATCH /api/orders/:id/complete`(완료 처리),
  `POST /api/orders`(요청 바디에 매장 내/포장 구분 `orderType` 포함),
  `POST /api/uploads`(이미지 파일을 Cloudflare R2에
  업로드하고 공개 URL 반환), `GET /health`(DB에 접근하지 않는 가벼운
  헬스체크 — Render 자체 헬스체크와 무료 티어 슬립 방지용 외부 핑에 사용),
  `POST /api/admin/login`/`GET /api/admin/session`/`POST /api/admin/logout`
  (관리자 로그인/세션 확인/로그아웃)
- `packages/types`의 `CreateOrderInput`, `UploadImageResponse`,
  `AdminLoginInput`, `AdminSessionResponse`, `UpdateSoldOutInput`,
  `CategoryInput`, `ProductInput`, `ReorderProductsInput`을 프론트엔드와
  함께 사용해 요청/응답 계약을 공유. `Product.category`는 고정
  union(`'coffee'|'ade'|'dessert'`)이 아니라 `string`으로 바뀌어
  관리자가 등록한 어떤 카테고리 이름도 가리킬 수 있음. `Product.order`
  (같은 카테고리 안에서의 순서)가 엔티티엔 있지만 생성/수정 요청
  바디엔 필요 없어서, 요청 바디 타입을 `Omit<Product, '_id'>` 대신
  별도 `ProductInput`으로 분리함(`CategoryInput`과 같은 패턴)
- Cloudflare R2 연동은 `src/lib/r2Client.ts`(`@aws-sdk/client-s3` 기반)에서
  담당하며, `multer`로 업로드된 파일을 메모리에 받아 R2로 전달
- 관리자 인증은 `express-session` + `connect-mongo`(기존 `MONGO_URI`
  재사용) 기반 세션이며, `src/middleware/requireAdmin.ts` 미들웨어가
  `POST/DELETE /api/products`, `POST /api/uploads`를 보호합니다. 세션
  쿠키를 프론트엔드(Vercel)와 주고받기 위해 CORS를 `FRONTEND_ORIGIN` 단일
  오리진 + `credentials: true`로 설정했습니다 — [[관리자인증인가]] 참고.

## 아키텍처 방향 메모 — 백엔드를 Next.js로 합치지 않고 분리 유지

**TL;DR**: 웹 키오스크뿐 아니라 향후 React Native 모바일 앱도 만들 계획이
있어([[기획서]] 범위 확장 시 반영 예정), `apps/backend`(Express)를
`apps/frontend`의 Next.js API Route로 흡수하지 않고 지금처럼 독립된
백엔드로 유지하기로 함. 지금 당장 처리할 작업은 아니고, 향후 구조를 정할
때 참고할 방향 메모.

**왜 이 논의가 나왔나**: `/admin` 관리자 인증을 만들며 프론트(Vercel)와
백엔드(Render)가 다른 오리진이라 CORS를 신경 써야 했던 걸 계기로, "차라리
백엔드를 Next.js API Route로 합쳐서 같은 오리진으로 만들면 더 간단하지
않을까"라는 질문이 나왔음.

**클라이언트가 웹 하나뿐이라면** Next.js API Route로 합치는 쪽이 실제로
더 단순했을 것(같은 오리진이라 CORS 자체가 불필요, 배포 대상도 Vercel
하나로 통합). 이 경우 `packages/types`, `packages/ui` 같은 공유 패키지와
Turborepo도 존재 의미가 줄어서 단일 Next.js 프로젝트로 단순화하는 것도
합리적인 선택지였음.

**하지만 모바일 앱 계획 때문에 결론이 바뀜**:
- React Native 앱도 결국 이 백엔드의 REST API를 호출해야 함. Next.js API
  Route도 기술적으로는 모바일에서 호출 가능하지만, 그러면 API가 "특정 웹
  프론트엔드 프로젝트의 부속물"이 되어 프론트 UI만 바꿔도 API가 같이
  재배포되는 등 결합이 생김. 웹/앱이 동등하게 의존하는 **독립된 백엔드
  서비스**로 두는 게 구조적으로 더 깔끔함.
- 앱이 웹(Next.js) + 모바일(React Native) + 백엔드(Express) 3개가 되면
  `packages/types`(공유 계약 타입)와 Turborepo 모노레포 구조가 다시
  확실한 존재 이유를 가짐 — 지금 구조를 그대로 확장하면 됨.
- **인증 방식 관련 참고**: 지금 관리자 인증(`express-session` 쿠키 기반,
  [[관리자인증인가]])은 매장 스태프가 웹으로만 쓰는 화면이라 문제없음.
  다만 앞으로 [[멤버십포인트조회]] 같은 **고객용 로그인**을 만들 때는
  웹/모바일 양쪽에서 써야 하므로, 쿠키 세션보다 토큰 기반(JWT를
  `Authorization` 헤더로 전달)이 React Native와 궁합이 좋음 — 브라우저가
  아닌 앱은 쿠키 자동 관리가 안 되기 때문. 그 기능을 실제로 만들 때
  다시 검토.

**결론**: 지금 구조(Turborepo 모노레포 + `apps/backend` 분리)를 유지한다.
실시간 주방 디스플레이(KDS, WebSocket 필요)도 서버리스보다 지속 연결이
가능한 별도 서버가 유리해서 같은 결론을 지지함. 모바일 앱 착수가
확정되면 `apps/mobile`을 추가하는 흐름이 될 것.

> 이 메모는 방향성 논의 요약이며, 실제로 모바일 앱 착수가 확정되는 등
> 구조가 확정되면 `docs/decisions/`에 정식 ADR로 남기는 것을 권장합니다
> (`docs/AGENTS.md` 참고).

- [x] 장바구니 항목별 수량 개별 조절(+/-)·삭제 기능 추가 (기존에는 메뉴

- [x] 관리자 인증 추가 — 공유 비밀번호 기반 로그인/세션으로 `/admin`과
  메뉴 등록/삭제/이미지 업로드 API를 보호 (`docs/specs/001-admin-auth`)
- [x] 관리자 메뉴 수정 기능 추가 — 목록에서 바로 이름/가격/이미지/
  카테고리를 수정(`PUT /api/products/:id`, `requireAdmin`으로 보호)
- [x] 관리자 품절 처리 기능 추가 — 목록에서 클릭 한 번으로 품절/판매
  재개 토글(`PATCH /api/products/:id/sold-out`), 고객 화면에서는 품절
  메뉴를 흑백 처리하고 장바구니 담기를 막음([[메뉴수정품절처리]] 참고)
- [x] 운영 환경에서 관리자 세션 쿠키가 안 심기던 문제 수정 —
  `app.set('trust proxy', 1)` 추가. Render는 앞단 프록시(Cloudflare)가
  HTTPS를 종료하고 내부적으론 HTTP로 전달하는데, 이걸 신뢰하지 않으면
  Express가 연결을 안전하지 않다고 판단해 `cookie.secure: true`인 세션
  쿠키를 아예 Set-Cookie에 실지 않았음. 그 결과 로그인은 성공 응답이
  왔지만 이어지는 메뉴 수정/품절 처리가 전부 401로 실패했음
  ([[관리자인증인가]] 참고)
- [x] 매장 내(Dine-in)/포장(Takeout) 선택 추가 — 키오스크 첫 화면에서
  매장/포장을 먼저 선택해야 메뉴 목록으로 넘어가고, 선택값이
  `POST /api/orders`의 `orderType`으로 함께 저장됨. 주문 성공 시 다음
  손님을 위해 선택 화면으로 돌아감([[매장내포장선택]] 참고)
- [x] 테이블 번호 입력 기능은 필요 없다고 판단해 백로그에서 제거
- [x] 관리자 "주문 내역" 탭 추가 — `/admin`에서 들어온 주문을 최신순으로
  확인(10초 자동 갱신 + 수동 새로고침). 검색/필터, 주문 상태 변경은
  아직 없음([[주문내역조회]] 참고). 겸사겸사 `Order.items` 공유 타입이
  실제 저장 형태(`CartItem[]`)와 어긋나 있던 걸 발견해 `OrderItem`
  타입으로 바로잡음
- [x] 관리자 페이지 데스크탑 레이아웃 개선, 주문 항목에 메뉴 이미지
  스냅샷(`OrderItem.imageUrl`) 추가 — PC에서 주로 쓰는 화면인데 글자/
  이미지가 작았던 문제 개선
- [x] 주문 내역에 주문번호·날짜 표시 추가 — `Order.orderNumber`는
  MongoDB `_id` 대신 KST 기준 당일 자정부터 1번씩 다시 매기는 짧은
  번호(스타벅스 매장 주문번호 방식). 별도 카운터 컬렉션 없이 주문 생성
  시점에 오늘 자정 이후 주문 수를 세어 계산 — 동시 주문 시 번호가
  겹칠 수 있는 트레이드오프가 있음([[주문내역조회]] 참고)
- [x] 주문 완료 처리 추가 — `Order.isCompleted`(기본값 false)와
  `PATCH /api/orders/:id/complete`로 완료 처리하면 "진행중 주문" 탭에서
  빠지고 "지난 주문" 탭(`GET /api/orders?status=completed`)으로
  이동함. 접수/준비중처럼 더 세분화된 단계는 아직 없음
  ([[주문상태전이-API]] 참고)
- [x] 카테고리 관리 추가 — 고정 enum(`coffee`/`ade`/`dessert`)이던
  카테고리를 관리자가 `/admin`의 "메뉴 관리" 탭 안 카테고리 칩 바에서
  자유롭게 추가/수정/삭제할 수 있게 함. 상품은 카테고리를 id가 아니라
  이름 문자열로
  참조해서, 이름 수정 시 상품도 함께 갱신(`Product.updateMany`)되고
  삭제 시 소속 상품도 함께 삭제(`Product.deleteMany`)됨. 기존 상품
  데이터를 손대는 마이그레이션 없이, 서버 시작 시 `Category` 컬렉션이
  비어 있으면 `Product.distinct('category')`로 자동 시딩
  (`ensureDefaultCategories`)해 안전하게 전환함([[카테고리관리]] 참고)
- [x] 카테고리 순서 변경 기능 추가 — `Category.order`(숫자, 작을수록
  앞)와 `PATCH /api/categories/reorder`로 관리자가 ▲/▼ 버튼으로 순서를
  바꿀 수 있음. 이 순서는 고객 화면 카테고리 필터와 메뉴 등록/수정 폼의
  카테고리 목록에도 그대로 반영됨. `order` 필드가 없던 기존 카테고리는
  서버 시작 시 이름순으로 자동 부여(`ensureCategoryOrder`)
- [x] "메뉴 관리"와 "카테고리 관리" 탭 통합 — 별도 탭이던 카테고리
  관리를 "메뉴 관리" 탭 안의 카테고리 칩 바로 옮기고, 칩을 클릭하면
  그 카테고리의 메뉴만 필터링되게 함(`AdminPage`가 `selectedCategory`
  상태를 들고 `ManageCategoryList`/`ManageProductList`에 함께 전달).
  선택된 카테고리 이름을 바꾸면 필터도 따라가고, 선택된 카테고리를
  삭제하면 필터가 "전체"로 돌아감([[카테고리관리]] 참고)
- [x] 카테고리 칩 드래그 앤 드롭으로 순서 변경 — 처음엔 브라우저 네이티브
  HTML5 드래그(`draggable` 속성)로 구현했는데, 칩 안에 버튼이 여러 개
  겹쳐 있어 브라우저/기기에 따라 드래그 시작 자체가 인식되지 않는
  문제가 실사용에서 나옴(터치 기기는 애초에 미지원). **포인터 이벤트
  (mouse/touch/pen 통합) 기반 커스텀 드래그**로 다시 구현해 해결함 —
  칩 앞 전용 손잡이(⠿)에서 `pointerdown`으로 시작해 `window`의
  `pointermove`로 좌표 hit-test하며 화면만 즉시 재배치하다가
  (`reorderLocally`, API 호출 없음), `pointerup`에서 한 번만 서버에
  저장(`commitCategoryOrder`). ◀▶ 버튼도 대안으로 남겨둠([[카테고리관리]]
  참고)
- [x] 고객 화면 카테고리 필터에서 "전체" 옵션 제거 — 손님이 전체보기
  화면에서 실제로 메뉴를 고르지 않는다는 실사용 관찰에 따라, 메뉴를
  불러오면 항상 첫 번째 카테고리가 자동 선택되도록 바꿈
  (`ProductList.tsx`). 관리자 화면("메뉴 관리" 탭)의 "전체" 필터는
  전체 메뉴를 한눈에 보며 관리하는 워크플로우가 여전히 필요해 그대로
  유지함([[카테고리별메뉴조회]] 참고)
- [x] 관리자 메뉴 등록을 "+ 메뉴 추가" 버튼 + 모달 방식으로 변경 — 기존엔
  등록 폼이 메뉴 목록 옆에 항상 펼쳐져 있었는데, 목록을 더 넓게 보여주고
  화면을 덜 복잡하게 하려고 버튼 클릭 시 여는 모달로 바꿈. 범용
  `Modal` 컴포넌트를 `shared/ui`에 새로 만들어(배경 클릭/✕/ESC로 닫기)
  다른 기능에서도 재사용할 수 있게 함. `AddProductForm`은 카드
  껍데기(제목/배경)를 스스로 그리는 대신 `Modal`이 감싸도록 폼만 남기고,
  등록 성공 시 호출되는 `onSuccess` 콜백을 추가해 모달이 자동으로
  닫히게 함([[메뉴등록]] 참고)
- [x] 메뉴(상품)도 카테고리 순서 변경과 같은 방식으로 순서 변경 추가 —
  `Product.order`(카테고리 안에서만 의미 있음)와
  `PATCH /api/products/reorder`로, "메뉴 관리" 탭에서 **특정 카테고리를
  골랐을 때만**(전체 보기 중엔 카테고리가 섞여 있어 순서가 무의미해
  숨김) 드래그 손잡이(⠿)와 ▲▼ 버튼이 나타남. 카테고리 드래그 때 만든
  포인터 이벤트 기반 커스텀 드래그 패턴(손잡이 `pointerdown` → `window`
  `pointermove`로 hit-test하며 로컬 재배치 → `pointerup`에 한 번만 저장)
  을 그대로 재사용. 새 메뉴는 그 카테고리 안에서 맨 뒤 순서로 등록되고,
  `order` 필드가 없던 기존 메뉴는 서버 시작 시 카테고리별 생성순으로
  자동 부여(`ensureProductOrder`). `POST/PUT /api/products`의 요청
  타입을 `Omit<Product, '_id'>`에서 별도 `ProductInput`(카테고리
  `CategoryInput`과 같은 패턴)으로 분리해, `order`가 상품 엔티티엔
  필요하지만 생성/수정 요청 바디엔 필요 없는 것을 타입으로 표현함
  ([[메뉴수정품절처리]] 참고)

## 다음 우선순위 로드맵

아래 항목 중 실제 작업을 시작하는 항목은 `docs/AGENTS.md`의 SDD 워크플로우에
따라 LeanSpec으로 개별 스펙(`docs/specs/`)을 만들고 진행 상태를 추적합니다.
이 문서는 우선순위 개요만 담고, 항목별 상세 설계/작업 분해는 해당 스펙에
기록합니다.

1. **결제 연동 여부 결정** (최우선) — 주문 생성까지만 구현되어 있어, 실제
   결제 수단을 붙일지 매장에서 별도 결제할지 먼저 결정이 필요합니다.
2. **주문 상태 흐름 설계** — 접수/준비중/완료 등 상태 전이가 필요한지
   검토합니다.
3. **테스트 도입** — 현재 프론트엔드/백엔드 모두 자동화된 테스트가
   없습니다. 주문/재고 관련 로직부터 우선 커버합니다.
4. **배포 파이프라인 정비** — 배포 대상은 Vercel(frontend) / Render
   (backend, 무료 티어)로 전환 완료했고 슬립 방지용 헬스체크(`GET
   /health`)도 붙어 있습니다. 운영 환경변수(`NEXT_PUBLIC_API_URL`,
   `MONGO_URI`, `R2_ENDPOINT`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`,
   `R2_BUCKET_NAME`, `R2_PUBLIC_URL`, `ADMIN_PASSWORD`, `SESSION_SECRET`,
   `FRONTEND_ORIGIN`)는 2026-09-07에 Render에 전부 등록해 운영 환경에서도
   관리자 로그인이 정상 동작함을 확인했습니다([[관리자인증인가]],
   `docs/specs/001-admin-auth` 참고). 남은 일은 프론트/백엔드 CI
   연동입니다 (현재 `.github/workflows/`에는 `docs/` Quartz 배포
   워크플로만 있음).
   > ⚠️ `FRONTEND_ORIGIN`은 트레일링 슬래시 없이 정확한 오리진만
   > 넣어야 합니다(`https://.../app` ✅, `https://.../app/` ❌) — `cors`
   > 패키지가 값을 그대로 `Access-Control-Allow-Origin`에 반영할 뿐
   > 정규화하지 않아서, 슬래시 하나 차이로도 브라우저가 CORS를 막습니다.
   > ⚠️ Render 같이 앞단에 프록시가 있는 배포 환경에서는
   > `app.set('trust proxy', 1)`이 없으면 `secure: true`인 쿠키(세션
   > 등)가 아예 발급되지 않습니다. 새 배포 대상을 추가할 때마다 이
   > 설정이 있는지 확인하세요.
5. **Tailwind 설정 정리** — 루트 `tailwind.config.ts`가 앱별 공용 설정
   패키지(`packages/config`) 없이 단독으로 존재합니다. 앱이 늘어나면
   통합을 검토합니다.
6. **관리자 역할 구분/감사 로그 검토** — 현재는 공유 비밀번호 하나로만
   인증하며 점주/직원 구분이나 조작 이력이 없습니다([[관리자인증인가]]
   참고). 필요해지면 별도 스펙으로 착수합니다.
